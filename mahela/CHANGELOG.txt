MahFLA Prototype — Changelog
==============================

v1.20.1 — Current
------------------
- Add Session's date picker no longer requires picking a year, and no
  longer allows a past date -- both per explicit request, since a new
  session is always being booked for today or later. The Year
  dropdown is gone entirely for this specific picker; the month list
  instead becomes a rolling 12-month window starting at the current
  month, so each month name still appears exactly once with no
  ambiguity about which year it falls in (the year is still tracked
  correctly underneath, just never shown or picked directly). For the
  current month specifically, the day list starts at today, not the
  1st; every other month in the window is inherently in the future,
  so its full day range is offered normally.
  Manage Session (editing a session that may already be in the past)
  is intentionally unchanged -- still shows all three dropdowns,
  including Year, and still allows any date. Verified this
  specifically: selecting a genuinely past date there still works
  exactly as before.
  Verified the new mode thoroughly, including the trickiest case --
  a selection wrapping from the end of one year into the next, in
  both Gregorian and Jalali terms -- with a reverse-conversion check
  confirming the resulting date is exactly right, and that switching
  language mid-selection doesn't shift the underlying date.

v1.20.0
--------
- Fixed session times showing Latin digits in Persian mode (e.g.
  "17:00 – 18:00" instead of "۱۷:۰۰ – ۱۸:۰۰"). Traced it to an
  inconsistency: one page (teacher schedule) already handled this
  correctly with its own local helper, but two others (the teacher's
  per-student schedule view, and the student's own panel) never got
  the same treatment, since each page had to remember to build its
  own copy of the conversion. Exported a single, shared version from
  the calendar module so every page now uses the same correct
  implementation, and fixed both places that were missing it (times
  and session durations).
- Redesigned the Teacher Profile popup students see -- previously a
  plain, unstyled stack of label/value text that looked unfinished.
  Now has a soft-tinted header panel behind the photo and name,
  icon-plus-value rows for email and phone instead of bare
  right-aligned text, and a distinct quote-styled card for the bio.
- Rebuilt the Hour/Minute entry in Add Session and Manage Session
  from the ground up, fixing a real, reported bug and a real,
  requested change:
  - The two fields were visually swapped -- caused by the page's
    right-to-left direction reversing their left-to-right DOM order.
    Time notation is read left-to-right even in Persian, so the
    picker's container now has its direction explicitly locked,
    regardless of the page's own direction.
  - Replaced the dropdown-based picker with two clearly labeled
    ("Hour" / "Minute") manually-typed fields, per explicit request
    -- much faster than scrolling a 60-item list, and now the only
    way to enter a time anywhere in the app. Accepts Persian digit
    input directly, rejects out-of-range values with a visible error
    state rather than silently correcting them, and blocks saving
    until fixed.
- Verified all of the above end-to-end through the real save
  handlers on every page they touch, then re-ran the full 13-page
  load audit -- no regressions.

v1.18.0
--------
- New: a brand-new student's Schedule tab now shows a proper "No
  sessions yet" message instead of a blank area with nothing in it,
  which looked broken. Verified with a genuinely fresh student
  record (zero sessions).
- Fixed a real bug: picking a session date in Persian always showed
  the browser's own Gregorian date picker, no matter the language --
  this is a hard limitation of the native date input itself, which
  cannot be made to show Jalali by any CSS or JS. Replaced it
  everywhere a date needs to be picked (Add Session and Manage
  Session on the student page, Manage Session on the teacher
  schedule) with a real Day/Month/Year picker built for this app,
  which shows Jalali when Persian is active and Gregorian otherwise,
  always storing a standard Gregorian date underneath. Verified
  end-to-end through the real save handlers on all three, including
  that double-booking conflict detection still correctly blocks an
  overlapping time through the new picker.
- While building this, found and fixed a genuine bug in switching
  language mid-selection: the picker was reinterpreting an
  already-chosen date using the newly active calendar system instead
  of the one it was actually chosen in, silently corrupting the date.
  Fixed by having the picker remember which calendar its current
  selection belongs to. Verified with a dedicated test: pick a date
  in Persian, switch to English, confirm the same real date is still
  shown, and back again.
- Investigated a reported Jalali/Gregorian round-trip mismatch for
  one specific historical date. Traced it to a documented, extremely
  rare edge case in the standard date-conversion algorithm this app
  (and most Persian-calendar software) uses: year 1404 is one of only
  two years between 1865-2152 where this well-established, widely
  used approximation diverges by a single day from the true
  astronomically-observed calendar, per an independent, respected
  calendar-science reference. Attempted a targeted fix; it corrected
  the reported date but shifted Nowruz itself by a day in testing --
  a worse, more visible error -- so reverted to the original,
  time-tested formula rather than risk that regression. Net effect:
  everywhere in the app is correct except one specific day (in the
  Dey/Jadi range) in the 1404 Jalali year specifically, which is
  isolated and does not affect the current year or any other.
- Full project-wide validation and the full 13-page load audit both
  run clean after every change in this version.

v1.15.1
--------
- Full-project audit at the user's request: ran every page through a
  real script execution (not just syntax checking) for the first
  time as a batch, rather than testing individual functions in
  isolation as before. Found two critical, page-breaking bugs that
  had gone undetected specifically because prior testing exercised
  functions directly rather than a full page load with all its event
  wiring active:
  - student-detail.html and teacher-students.html both had a
    function that was simultaneously (a) a listener for
    mahtela:langchange and (b) calling window.mahtelaI18n.apply(),
    which itself dispatches mahtela:langchange. Every render
    triggered another render, infinitely, overflowing the call stack.
    This would have hung or crashed both pages on essentially every
    load in a real browser -- and since it happens mid-script, every
    initialization statement after the point of failure (message
    composer setup, additional event listeners, etc.) would silently
    never run either.
  - Fixed by removing the unnecessary global apply() call from
    student-detail.html's renderScheduleTab (its dynamic content
    already translates itself directly and never needed it), and by
    translating teacher-students.html's dynamic card text directly
    via dictionary lookup instead of relying on the global scan,
    since that page's cards do need translation.
  - Verified via full script execution on all 13 pages: all pass
    cleanly after the fix, where 2 previously failed.
  - Also checked every other place that triggers a mahtela:* custom
    event for the same dispatch-from-within-your-own-listener
    pattern; none of the others exhibit it.
- Everything else audited clean: JS syntax, HTML tag balance, CSS
  balance, i18n key coverage, DOM id references, internal links, and
  duplicate ids -- no other issues found in this pass.

v1.13.0
--------
- Fixed a real navigation bug: clicking "Messages" in the sidebar while
  already on student-panel.html did nothing, though the exact same
  link worked fine when clicked from Settings. Root cause: the tab
  deep-link logic (open the tab named in the URL hash) only ran once,
  on the initial page load -- a same-page anchor click just updates
  the hash without a full reload, so it never ran again. Now also
  listens for the hashchange event and re-applies. Verified with a
  real DOM simulation of the exact reported scenario, not just the
  "works on fresh load" case that was already passing.
- Role-based chrome color: the teacher and admin panels no longer
  share the same pink used for female-student gender accents. Teacher
  pages now use gold (#F7B801), admin pages use indigo (#7678ED), both
  scoped via a single [data-role] attribute on <html> so every
  existing component that already references var(--brand) picks up
  the right color automatically -- no per-component overrides needed.
  Checked ink-text contrast on both new colors (teacher ~9.9:1 base /
  ~7.7:1 hover, admin ~5:1 base / ~6:1 hover) before committing to
  them; all clear WCAG AA. Replaced several chrome-related hardcoded
  pink rgba() values (shadow glow, badges, focus rings) with proper
  tokens so they respect the role color too, instead of just the
  --brand/--brand-strong properties that were already variables.
  While doing this, caught and fixed a real cross-contamination bug it
  would otherwise have introduced: female students' own accent color
  (--student-accent-strong) was defined as var(--brand-strong), so on
  a teacher-role page (student-detail.html) it would have silently
  inherited the teacher's gold instead of staying pink. Decoupled it
  to a fixed value. Settings.html (which serves all three roles from
  one file) sets the attribute dynamically based on which role's
  section is active.
- Dashboard titles now say which role they belong to: "Dashboard"
  became "Teacher Dashboard" and "Overview" became "Admin Dashboard",
  in both the page heading and the browser tab title.
