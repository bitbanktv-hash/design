MahFLA Prototype — Changelog
==============================

v1.16.0 — Current
------------------
- Admin can now edit and delete teacher accounts -- previously the
  admin panel only allowed suspend/reactivate, permissions, and
  password reset, with no way to correct a teacher's name/email/phone
  or remove an account entirely. Added Edit and Delete actions to
  each teacher row, with a proper confirmation step before deleting
  (not a raw browser confirm() -- a real modal matching the rest of
  the app). Verified end-to-end: editing saves correctly, deleting
  removes only that teacher and leaves everyone else untouched, and
  confirmed no other page crashes if a student's assigned teacher no
  longer exists (the lookups already handled that gracefully).
- Fixed the admin panel dropping straight into the teacher's own
  view when clicking through to a student's profile -- from either
  Admin > Students or Admin > Teachers > a teacher's student list,
  the admin previously saw Jane Doe's own sidebar, colors, and nav,
  as if they'd become her. student-detail.html now detects who's
  actually viewing it and shows proper admin chrome (admin sidebar,
  admin nav, "Site Admin" identity, admin's own color) when reached
  from the admin panel, while the teacher's own experience is
  completely unchanged when reached normally. While wiring the two
  admin-panel links to signal this, caught and fixed a mistake in my
  own edit before it shipped -- a dropped opening quote that would
  have broken both pages' student tables -- via the same validation
  pass this project always runs before any push.
- Investigated a reported date bug ("Student Since" showing Gregorian
  in Persian) in depth: reproduced the exact symptom, traced it to a
  leftover explicit "Gregorian" calendar preference from testing
  before the "Automatic" option existed (added last version) --
  confirmed the underlying code is correct in the default state.
  Additionally wrote a script that loads every page in Persian and
  scans all rendered dates for any Gregorian leakage; found one false
  positive (an artifact of concatenating adjacent elements' text
  without the whitespace a real render would have) and no other
  issues.
- Re-ran the full 13-page load audit and all 22 interaction tests
  from the previous pass after every change in this version -- all
  still pass, confirming no regressions.

v1.15.1
--------
- Full-project audit at the user's request: ran every page through a
  real script execution (not just syntax checking) for the first
  time as a batch, rather than testing individual functions in
  isolation as before. Found two critical, page-breaking bugs that
  had gone undetected specifically because prior testing exercised
  functions directly rather than a full page load with all its event
  wiring active:
  - student-detail.html and teacher-students.html both had a
    function that was simultaneously (a) a listener for
    mahtela:langchange and (b) calling window.mahtelaI18n.apply(),
    which itself dispatches mahtela:langchange. Every render
    triggered another render, infinitely, overflowing the call stack.
    This would have hung or crashed both pages on essentially every
    load in a real browser -- and since it happens mid-script, every
    initialization statement after the point of failure (message
    composer setup, additional event listeners, etc.) would silently
    never run either.
  - Fixed by removing the unnecessary global apply() call from
    student-detail.html's renderScheduleTab (its dynamic content
    already translates itself directly and never needed it), and by
    translating teacher-students.html's dynamic card text directly
    via dictionary lookup instead of relying on the global scan,
    since that page's cards do need translation.
  - Verified via full script execution on all 13 pages: all pass
    cleanly after the fix, where 2 previously failed.
  - Also checked every other place that triggers a mahtela:* custom
    event for the same dispatch-from-within-your-own-listener
    pattern; none of the others exhibit it.
- Everything else audited clean: JS syntax, HTML tag balance, CSS
  balance, i18n key coverage, DOM id references, internal links, and
  duplicate ids -- no other issues found in this pass.

  session's date, time, and duration, instead of only being able to
  cancel it -- in both the weekly schedule view and the per-student
  detail view. The schedule view also re-checks for a double-booking
  conflict when rescheduling, using the same check as booking a new
  session. Verified both the happy path and that a genuine conflict
  correctly blocks the save.
- New: teachers can set a specialization/language-taught and a short
  bio in Settings > Teaching Profile. Students now see their actual
  teacher's name and specialization on their panel (previously
  hardcoded "Jane Doe · English" regardless of who their real teacher

  edit in Settings shows up correctly on the student's side.

v1.14.0
--------
- Fixed a severe bug: the teacher's weekly schedule opened completely
  blank -- no calendar at all. Root cause found via actually executing
  the page's script (not just checking syntax): the schedule already
  filtered STUDENTS down to just this teacher's own students, but
  SESSIONS was still loaded unfiltered. The moment the visible week
  contained a session belonging to another teacher's student (several
  of the 21 seeded sessions do), the render crashed trying to look up
  a student that didn't exist in the filtered map, and nothing after
  that point ever rendered. Filtered sessions the same way at load
  time. While fixing this, caught a second, more serious bug the
  naive fix would have caused: saving a session would have silently
  overwritten the entire shared sessions store with only this
  teacher's own sessions, deleting every other teacher's classes.
  saveSessions now merges this teacher's current state back with
  everyone else's untouched sessions instead. Verified both with a
  real script execution and a save/reload simulation.
- Settlement history dates were showing both calendars stacked
  together (e.g. "Jun 1, 2026 | 1405/Tir/10"), which read as garbled.
  Changed to show a single calendar based on language/preference,
  matching how every other date in the app already behaves.
- Finished applying the teacher/admin role colors everywhere: the
  main sidebar logo badge, the clock widget icon, the teacher's own
  avatar (sidebar and chat bubbles), and the highlighted Finance stat
  card were all still hardcoded to the pink/teal gradient regardless
  of role -- the most visible offender being the logo itself, shown
  on every single page. Also fixed a genuine contrast violation found
  in the process (white text sitting directly on the logo's gradient).
- The sidebar's own "Dashboard" nav link/tab, not just the page
  heading, now says "Teacher Dashboard" or "Admin Dashboard" -- this
  is specifically what was meant by the earlier request, which the
  page-heading change alone didn't cover.
- Added an explanatory note under the required email/mobile fields in
  Settings' Personal Details, explaining they're used for
  notifications and contact. The required + valid-format enforcement
  itself was already correctly wired from earlier work; only the
  explanatory hint was missing.

v1.13.0
--------
- Fixed a real navigation bug: clicking "Messages" in the sidebar while
  already on student-panel.html did nothing, though the exact same
  link worked fine when clicked from Settings. Root cause: the tab
  deep-link logic (open the tab named in the URL hash) only ran once,
  on the initial page load -- a same-page anchor click just updates
  the hash without a full reload, so it never ran again. Now also
  listens for the hashchange event and re-applies. Verified with a
  real DOM simulation of the exact reported scenario, not just the
  "works on fresh load" case that was already passing.
- Role-based chrome color: the teacher and admin panels no longer
  share the same pink used for female-student gender accents. Teacher
  pages now use gold (#F7B801), admin pages use indigo (#7678ED), both
  scoped via a single [data-role] attribute on <html> so every
  existing component that already references var(--brand) picks up
  the right color automatically -- no per-component overrides needed.
  Checked ink-text contrast on both new colors (teacher ~9.9:1 base /
  ~7.7:1 hover, admin ~5:1 base / ~6:1 hover) before committing to
  them; all clear WCAG AA. Replaced several chrome-related hardcoded
  pink rgba() values (shadow glow, badges, focus rings) with proper
  tokens so they respect the role color too, instead of just the
  --brand/--brand-strong properties that were already variables.
  While doing this, caught and fixed a real cross-contamination bug it
  would otherwise have introduced: female students' own accent color
  (--student-accent-strong) was defined as var(--brand-strong), so on
  a teacher-role page (student-detail.html) it would have silently
  inherited the teacher's gold instead of staying pink. Decoupled it
  to a fixed value. Settings.html (which serves all three roles from
  one file) sets the attribute dynamically based on which role's
  section is active.
- Dashboard titles now say which role they belong to: "Dashboard"
  became "Teacher Dashboard" and "Overview" became "Admin Dashboard",
  in both the page heading and the browser tab title.

v1.11.0
--------
- Fixed a real, load-bearing bug found via screenshots: the session
  Status buttons (Scheduled/Held/Cancelled) in the Manage Session
  modal didn't work at all -- clicking did nothing, and they rendered
  as plain unstyled text instead of buttons. The seg-control component

  -> apply a fee -> save" flow end to end.

- Class duration is now typed manually as "H:MM" (e.g. "1:15") instead

  correctly; skill bars and displayed values were updated to match.
  Verified end-to-end: a score entered by the teacher shows up
  correctly, at the right chart position, on the student's own panel.

v1.9.0
--------
- Class type (In-Person / Online): selectable whenever a session is
  booked or edited (teacher-schedule.html's Book/Manage Session
  modals, student-detail.html's Add/Manage Session modals), shown as
  a badge next to the student's name everywhere a session appears --
  schedule grid blocks, session rows, the unsettled-sessions checklist.
- Session status is now a real state machine, not just Held/Scheduled:
  Scheduled / Held / Cancelled, with cancellation carrying who
  cancelled (teacher / student / student no-show) and whether the
  teacher chooses to charge for it. A no-show the teacher still
  travelled for can be billed; a cancellation with enough notice
  doesn't have to be. Finance calculations respect this -- only Held
  sessions and charged cancellations count toward what's owed.
- Teacher can leave a per-session note, visible to the student on
  their own Schedule tab (read-only there).
- Finance tab: the settlement-request box now auto-computes the
  session count and amount from whichever unsettled sessions are
  currently checked -- only the message text is teacher-editable --
  and actually sends that as a real message to the student via the
  shared messaging data, showing up in messages.html.
- Built a shared, localStorage-backed data layer (assets/js/
  sessions-data.js) so teacher-schedule.html, student-detail.html,
  student-panel.html, and messages.html all read and write the SAME
  session and conversation state instead of each hardcoding its own
  disconnected copy -- this is what makes "cancel a class -> the
  student sees it" and "request settlement -> a real message arrives"
  actually work across pages. Made it defensive against old-shape
  data already sitting in someone's localStorage from before these
  fields existed (backfills missing fields instead of producing
  undefined and breaking the UI) -- verified in Node.
- Fixed two real, pre-existing bugs found while wiring this up:
  student-detail.html's and student-panel.html's Messages tabs always
  showed Elena's hardcoded sample conversation regardless of which
  student's profile was actually open; both now show the real,
  correct thread for whichever student you're viewing.
- Sanitized the chat composer's output: it's a real contenteditable
  field, so a rich paste could previously carry arbitrary markup
  (script tags, onerror/onclick attributes, javascript: URLs) into
  stored messages that later get re-inserted as raw HTML. Now
  restricted to exactly the tags the toolbar itself produces
  (bold/italic/underline/line breaks); everything else is unwrapped
  to plain text. Verified against 8 attack patterns with a real DOM
  (jsdom) before trusting it, not just a hand-written mock.
- Ran a full end-to-end simulation of the real user flow (book ->
  cancel with a fee -> compute what's owed -> mark settled -> send a
  settlement message) in Node before considering this feature done,
  not just individual unit checks.

  Added messages.html, a real inbox with a conversation list (one per
  student, showing the last message and time) and a full message

  Messages tab so both surfaces work the same way.
- Fixed several more spots that were still using white text on the
  mid-tone brand colors, missed in the v1.6.0 contrast pass because
  they were inline styles rather than the shared stylesheet: sidebar
  and message-bubble avatars, the profile header avatar, and the
  teacher-strip avatar on the student panel.
- Fixed a dark-mode-only contrast regression introduced in the
  v1.6.0 fix itself: several rules switched avatar/button/bubble text
  from white to var(--ink) to fix light-mode contrast, but --ink
  flips to near-white in dark mode ([data-theme="dark"] --ink:
  #F3F0FB) while the backgrounds they sit on (--brand, --c-pink,
  --c-teal, --student-accent) don't change -- so those same elements
  went right back to a ~2.5:1 failure, just now only in dark mode.
  Switched all of them to the theme-stable --c-ink instead (same fix
  already used for the toast background in v1.6.0).
- Fixed the emoji picker rendering open by default on page load: its
  class set "display: grid" unconditionally, which -- as an author
  stylesheet rule -- overrides the browser's own "[hidden] {
  display: none }" UA rule. Added an explicit
  ".chat-composer__emoji-popover[hidden] { display: none; }" rule.
- Fixed modal Escape/focus behavior for two modals open at once (e.g.
  Reset Password opened from inside the Teacher's Students modal):
  the v1.5.0 keyboard handling picked the "topmost" modal by DOM
  order, not open order, so Escape could close the wrong one and
  focus could return to the wrong trigger. Modals now track an

- Added data-i18n-aria (translates aria-label + title together) and
  extended data-i18n-ph to also update a contenteditable composer's
  CSS-based placeholder, not just the native placeholder attribute --
  both needed for the new Messages toolbar/composer, both reusable
  for future icon buttons and rich-text fields.

v1.6.0
------------------

  (confirmed from your DevTools screenshot -- the DOM content was
  genuinely all there, "Elena Kim" and all, it just never became
  visible). The cause: the fade-in animation CSS required the
  .reveal-group element ITSELF to carry the .is-ready class

  before): profile photo upload with live preview, editable name/email,
  a gender selector, and a separate password-change form with mismatch
